## IPZZ-172 重下载为什么不能直接加入现有队列

只读预检时：1 个活动任务、19 个暂停任务、41 个已停止任务；未发现目标 infohash。活动任务按选中文件剩余约 1.065 GB，加 10% 承诺约 1.172 GB。媒体盘可用约 17.14 GB，配置底线约 10.24 GB，新候选选中文件加 10% 约 2.268 GB，当前快照算术可以容纳，但这不是原子资源预留。

已发现两个实际自动化风险：

1. `/downloads/recovery-*` 不是上传隔离区。现有完成搬运器枚举同一 RPC 的完成任务，会把选中视频搬到 `/movies`，之后上传器可能自动接单。因此不能靠新目录名字或 `pause=true` 宣称“人工验收前绝不上传”。
2. 主调度器在缺活动任务时可从全部暂停队列恢复任务。暂停队列剩余约 41.25 GB，另有大小未知任务，不能整体恢复；自建暂停任务也不是稳定保留状态。

后续安全方案需明确自动化所有权：独立固定镜像实例、只挂载下载和 movies 扫描根之外的全新目录，不注册现有 RPC、无完成钩子；同时持有主调度准入以记录额外约 2.3 GB 资源承诺。停止调度定时器不能等同停止正在传输的 aria2，也不能误停上传服务。具体实施前仍要核对所有准入 writer 和控制器，不能盲目执行。

上述为初始只读预检边界。后续已在扫描根之外实际预分配全新候选文件，并通过独立固定镜像实例开始受限恢复，详见 `IPZZ172_ISOLATED_RECOVERY_STARTED_20261024.md`；没有向主下载 RPC 添加 / 恢复 / 暂停任务，原件、种子及旧控制文件保留。候选仍未验证完整，不能上传或删源。
