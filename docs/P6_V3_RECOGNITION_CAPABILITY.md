# P6 V3 recognition capability (partial delivery)

## Implemented

- Shared `encryptcore.MediaRecognizer`: actual loopback-capable HTTP operation `recognize-record0`, strict 48-byte header, optional exact 16-byte streaming trailer, complete record0 + tag, speculative context-aware existing process KDF, in-place AEAD Open, then at most 4096 plaintext bytes to existing strict video classifier.
- Root opted-in protected filename mounts call this operation in their actual listing recovery flow. Default permits chunk <=1MiB (+16-byte tag); default 16MiB old objects are rejected after 48 bytes, without record download/allocation/KDF. `.bin` remains unchanged on denial/unknown signature. Result reasons and actual read/record bytes are inspectable.
- One active recognizer per proxy instance, at most two pending shared operations; handler independently admits one worker + two pending flights, eight-second listing wait/four attempts and five-second default worker deadline. Explicit trusted operator `alist.mediaRecognitionLargeRecordOptIn=true` authorizes at most one 32MiB record, with 30-second worker/operation deadline. It is not a URL/range hint, nor a newly exposed public recognition endpoint. Config updates are read at operation admission, and publication is runtime-revision fenced. No confirmation UI is claimed.
- Instance record byte lease is released on real completion; independent process byte admission is 64MiB, in addition to existing bounded process KDF admission. Instance stop closes admission, cancels HTTP/deadline and joins actual work. It does not close global KDF; a canceled PBKDF2 retains its global CPU slot until actual completion.
- Exact 206 geometry; 200 ignored Range is bounded only for offset zero, and tail requires 206. Reject transparent decompression/nonidentity encoding, truncated bytes, changed header/validator/scope, unexpected Vary and unsafe redirect schemes/userinfo. Redirects strip credentials on origin changes. No caller-controlled arbitrary headers beyond auth/cookie/user-agent are forwarded.
- Root V3 publication requires actual record authentication, video signature and one strictly parsed strong response ETag on every recognition response (RFC opaque entity-tag, surrounding OWS normalized; weak, unquoted, invalid opaque characters, combined lists and multiple header values rejected as freshness evidence). Invalid/missing validators do not prevent signature recognition but keep `Reusable=false`, so root cannot publish an alias. No unknown-revision record-cache reuse is added. Listing size alone never reuses persisted V3 aliases: every V3 listing/restore rechecks authenticated prefix; restore additionally compares saved ETag/geometry. Ordinary media request upstream authorization is still mandatory. Existing V1/V2 behavior remains.
- Explicit persisted V3 `fixed`/`trailer` layout and additive schema 2. Old V1/V2 aliases remain readable; V3 aliases without explicit layout require reinspection. No ciphertext bytes, V3 AAD, or old objects are changed.
- Mobile exports aliases to this same capability, avoiding duplicated HTTP/KDF/geometry logic. There was no actual mobile V2 video-signature alias recovery/store path to extend: filename decryption and confirmed metadata are different evidence.

## Authenticity / remaining boundaries

The only claim is **record0 authenticated + geometry checked + video signature**. Existing V3 empty AAD means header/trailer/PlainSize are not AEAD authenticated, nor is the whole file. Same record-count PlainSize mutation can pass geometry and record authentication; test documents acceptance rather than claiming cryptographic tamper detection. Empty objects have no record/signature and do not become video aliases. Unknown/truncated signatures do not cause additional record downloads.

Persisted alias restore reinspection is not full transactional version pinning of the subsequent playback response. Existing playback contracts retain their own checks. Strong ETag is conservative freshness evidence, not remote revision attestation. Shared capability intentionally does not reuse records against unknown revision (including token URL changes); integration with authenticated playback-record caches awaits reliable current-object revision/auth scope contract. Cross-instance byte admission is separate from playback record budget, with a combined configured upper bound, not one unified allocator.

Deferred: authorized user confirmation UI/API; actual mobile directory video-alias discovery, durable alias store, lifetime owner and revision-fenced publication; comprehensive end-to-end root/mobile UI flows and cloud execution. **This is not full P6 completion.** Large-record configuration authorizes expensive background recognize-record0 on existing protected mounts; leaving it false is the conservative default.
