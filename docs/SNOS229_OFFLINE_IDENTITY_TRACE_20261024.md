## DeletionEvent 是线索，不是文件已经永久消失的结论

`internal/handler/stats_store.go` 中该事件 ID 是本地 UnixNano，并非提供商 file ID。`webdav.go` 在 DELETE 上游返回 2xx 后记录事件；`alist.go` 的 fs/remove 业务成功及某些移动 / 覆盖路径也调用同一记录器。

因此现有事件不能区分具体方法、操作者或是否进入回收站，也不能证明提供商物理数据永久删除。它提供了精确可审计时间点，下一步应优先查这一小段历史请求日志 / 操作记录，而不是无限重复列同一目录。

后续只读穷举确认共五个生产记录调用点，历史 `84975d5` 与当前条件一致：DELETE / fs/remove 记录明确请求的源路径，不递归合成被删父目录的每个子文件；DAV MOVE / COPY 仅在覆盖目标返回 204 时记录目标路径，201 新目标和移走源路径不记录。fs/move / copy 根据目标缓存存在性记录目标，其中一处分支未排除源目标相同，故**同路径操作可能产生统计假阳性**。普通 fs/rename 也不单独产生源路径事件。事件本身仅有路径、时间和最近播放间隔，没有方法、操作者或提供商 ID，不能把它当作确定删除证明。

当前上传器的验收后本地删源只执行本地 rename / remove，不调用此网关事件记录；现存远端删除 helper 无调用点。但事故期上传器版本未证明留存，不能据当前源码归因历史操作者。上述网关删除处理也不会把 complete filename claim 改成 failed，故 complete 记录与后来路径不可见可以并存，不应靠释放 claim 来掩盖这种时间线。
