# SNOS-229：Docker不可播、安卓可播的现场诊断

## 已复现的直接故障

用户报告同一网络/手机安卓端可播，Docker端不可播。2026-10-18 12:29:02至12:29:30（+08）代理日志中目标`/dav/156联通云盘/encrypt/hhd800.com@SNOS-229.mp4`连续10次PROPFIND均404，大多0.08–0.13ms；未走到视频帧解码阶段。只读复测PROPFIND、HEAD、Range GET同样404，错误体为`Protected filename unavailable for this scope`。目录Depth1仍列出对应名称，长度属性为不可用404 propstat。

## 已核对的审计和上游

只读committed Bolt审计诊断找到唯一记录：

- 状态`failed`，密文长度4170019858。
- 创建2026-10-17T16:10:57.176564Z，更新16:21:12.418752Z。
- 原路径、当前加密规则、上游origin均匹配。
- 历史上传AuthScope与当前Basic不匹配，但**这不是当前直接拒绝条件**：`hasInvalidProtectedFilenameScope`首先要求状态complete；complete记录读取不要求复用上传AuthScope，standard模式另用当前调用方上游授权检查，trusted_local保持既定契约。
- 上游逻辑查询成功、非目录，明文长度4170019826，正好等于上述密文减32字节V2头；文件未因该404而消失。长度吻合不代表全片码流验证。

## 结论与修复方向

这是Docker现有原名保护门禁被遗留failed预留记录阻断，与安卓差异一致。不能据此认定媒体坏、网络坏或手机坏。PR101的preflight-before-reserve只阻止新污染，不回溯修复已有failed记录，因此该历史兼容问题仍存在。

不删除审计、不把failed直接改complete、不关闭guard、不覆盖/重传云文件。准备增加显式管理员操作：在授权校验、现存原始对象、当前规则和密文/解密几何/文件名证据成立后，写独立可审计恢复绑定，原失败记录保持原样；读取仅在严格匹配恢复证据时允许。当前尚未部署该恢复流程，不能说SNOS-229已恢复。

原始代理/上传日志保留本机私有，不对外提供可能含凭据及直链的原日志。此报告仅含脱敏诊断事实。
