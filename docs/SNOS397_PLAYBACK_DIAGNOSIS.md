## 后续本机代码与实际码流核验：修正初步判断

不能再把此问题主要解释为正常视频的关键帧稀疏。新增证据：

1. 对part001有限读取前19425771字节，依据stsz/stsc/stco定位前750个视频样本。样本75（偏移1967854）起出现全零内容；2MiB至本次19.4MB读取末尾各1MiB窗口均100%零。样本表仍将这些区域声明为有长度的视频样本，实际不能作为正常H.264 NAL解析。
2. 多次独立DAV Range在1967854、8388608、16777216处各读取1024字节，均全零。
3. **进一步绕过播放代理**，使用日志已有上游定位器直接读取原始V2密文，通过本机OpenSSL按代码规定的PBKDF2-SHA256（AES-CTR-v2，600000次）及头部nonce独立解密。先以ftyp验证选中规则，再复核上述三处，仍全部1024零字节，SHA256均为 `5f70bf18a086007016e948b04aed3b82103a36bea41755b6cddfaf10ace3c6ef`。因此这些零内容已存在于云端加密对象对应的明文，不是播放代理此次Range映射/缓存临时生成。
4. 本机实际分割代码 `/root/script/alistauto2.0/alist_uploader.py:1662–1682` 调用 `ffmpeg -ss START -i SOURCE -t DURATION -c copy OUTPUT`，无faststart，也没有重新编码；仅要求exit0和输出size>0，不检查视频包、解码结果、实际时长或有效帧。copy分割不会修复既有缺失视频数据，也不制造新关键帧。
5. `/root/script/alistauto2.0/alist_uploader.log:45151–45197` 记录20:12至20:46该文件实际切片上传：part0011858.05MB、part0021830.12MB、part003/004均0.00MB，最后20:46:11删除源文件并报成功。与云端后两片明文262字节吻合，**无效小片在上传前就已产生，不是仅云端显示错误**。
6. `_upload_file_sliced:1891–1912` 按估计时间机械递增，无分片媒体内容验收/总有效时长覆盖检查；没有fatal即mark_uploaded并删源。这是确定的本机交付校验漏洞。

## 初步结论与边界（被后续证据补充）

- **高置信：文件尾部moov导致播放器需要额外尾部请求，关键帧索引极稀疏，会显著影响seek定位。** 对前约117秒的很多位置，索引中前一个同步样本仍为开头，因此回到接近0是合理的候选机制。
- 索引稀疏有两种可能：实际编码关键帧就极稀疏，或文件分段/封装后stss不完整或错误。仅看容器索引无法判定是哪一种；未完整解析1.95GB码流，不能宣布视频损坏或确认全部实际IDR数量。
- 安卓端同现支持调查共同源文件，但不单独证明所有客户端/代理代码无错。
- 现有EOF与302缓存修复仍有价值，但不能补出视频缺失的随机访问关键帧，也不能据此保证此文件拖动问题消失。
- part003/004日志显示上游cipher294、plain262字节，明显不是正常GB视频；仅确认日志所报告大小，未擅自下载内容或判断这些小对象为何产生。

## 处理顺序

1. 先确认原始未加密源文件在同播放器中能否准确拖动，或取得原始文件的ffprobe/同步帧信息，区分源文件与上传后字节变化。
2. 以新输出文件做无损重新封装并把moov移到头部（faststart）可减少尾部索引往返；**仅移动moov不保证修好关键帧稀疏**。不覆盖现有云端对象。
3. 若重建封装后同步帧仍极稀疏，需重新编码并设置合适关键帧间隔，不能靠HTTP缓存或纯copy封装制造新关键帧。
4. 按用户实际拖动时间点再关联请求偏移，区分播放器回退选点、读流中断与数据映射问题。
