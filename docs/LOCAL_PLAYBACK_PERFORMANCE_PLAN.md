# 本地播放性能与体验优先优化计划

> 状态：用户已批准执行；阶段与证据见 `LOCAL_PLAYBACK_PERFORMANCE_EXECUTION.md`。本文件描述目标，不代表所有优化已完成或部署。
>
> 基线：本机已部署 `b6f2f1bbe02a0d1df2fa8ae411de163f3efde7a2`，发布 `v2026.10.17.472`，容器 healthy；该基线包含 PR #95 的 WebDAV 原名读取修复。
>
> 使用前提：用户明确选择可信本地、单用户使用，优先性能和体验，不以多用户权限隔离、每请求重新鉴权或严格实时新鲜度为目标。仍保留不丢文件、不误覆盖、正确解密、正确协议响应和可回滚。

## 1. 要达到的效果

围绕本机 Docker → OpenList → 联通云盘 → 手机 WebDAV 播放器这条实际链路，依次优化：

1. 点击能打开，不因上传 token 与 WebDAV 认证形式不同出现本地误拒绝。
2. 首次播放少走串行网络请求；重复打开、拖动和回播复用已有结果。
3. 原名反查不随历史上传记录数量线性变慢。
4. 目录能快速显示，文件长度、Range 和拖动行为与播放器预期一致。
5. 后台扫描、元数据探测、预热不与前台抢资源。
6. 通过请求次数、首个解密字节、手机首帧及拖动恢复时间证明收益，不以“CI 全绿”代替体验验收。

**第一轮范围是根程序/Docker。** Android 当前能秒开，作为同源对照；优先借鉴现有移动端实现，不先重写或改慢移动端。

## 2. 已知事实与不能夸大的结论

### 2.1 已核实的代码开销

| 环节 | 当前实现 | 本轮方向 |
|---|---|---|
| 受保护原名反查 | `internal/storage/filename_records.go` 的 `FindFilenameReservationForRead` 全表解析记录，预算 250ms | 可重建的反向读索引，查询不再全表扫描 |
| 播放前验证 | `internal/handler/media_name_recovery.go` 在原名绑定前额外执行 Depth:0 DAV 请求 | 可信本地模式移除该额外请求，实际读取仍正常发送到上游 |
| 播放元数据 | 根端 `playback_orchestrator.go` 已支持完整 `ContentMeta` 缓存 | 补统一逻辑对象身份、失效和并发合并，不另造第二套无关缓存 |
| 直链 | 已有 raw URL 缓存、过期判断及重定向解析 | 区分“直链更新”与“文件内容变更”，避免 URL 换签导致全链重探测 |
| V3/KDF/数据缓存 | 已有 KDF 有界调度、V3 认证 record 缓存和 V1/V2 明文块缓存 | 先测命中和派生次数，再调预算或补缺口，不能声称从零建设 |
| Android 对照 | 已有 confirmed metadata 持久化、并发合并和可选邻集预热 | 复用成熟契约；24h 元数据复用不等于永久严格最新 |

**存储纠正：** 原名占位/审计通过 `FileDAO.store` 使用本地 durable Store（Bolt）；即便部署配置了 MySQL，普通文件元数据与原名审计也不能当成同一个数据库。本轮原名索引必须跟随真实 Store 实现，不能只给 MySQL 加索引就算完成。

### 2.2 当前现场验证的边界

- WA-596.part003 已完成单文件 PROPFIND 207 和前 1KB Range GET 206，日志显示 V2 解密链路正常。
- 目录 Depth:1 返回约 1800 条，抽样 40 个文件的元数据查询成功。
- 这些结果不等于完整播放 40 个视频，也不等于已测得手机首帧、拖动和长时间稳定性。
- 现场曾出现 PROPFIND 长度 `2036812728`、GET 总长度 `2036812696`，相差 32 字节。必须重新解析完整响应确认是否暴露密文长度；若确认不一致，列为协议正确性缺陷，不沿用旧账本的“明文长度已验证”表述。
- 目录有/无末尾 `/` 的处理不同：现场带 `/` 正常，不带 `/` 曾被派生为加密文件名后 404，需要兼容性测试，不能一律盲目补斜杠。

## 3. 本地模式的明确取舍

建议新增配置 `alistServer.playbackProfile`，取值 `standard` / `trusted_local`，名称在实施时统一到实际配置风格。

- 对其他部署，默认 `standard`，保留原行为。
- 本机在优化通过后明确启用 `trusted_local`，不靠客户端 IP、User-Agent 或“看起来是局域网”猜测。
- 模式变更应可在 UI/运行诊断中看见，并使相关内存缓存换代，避免混用旧策略。

| 项目 | `trusted_local` 的决定 |
|---|---|
| 上传凭据与读取凭据摘要不一致 | 不作为原名读取拒绝条件 |
| 每个文件读取前的额外 DAV 权限复核 | 移除；实际 GET/PROPFIND/直链解析继续正常运行 |
| 已确认的本地 HEAD/元数据/明文块命中 | 可直接服务，不额外联网证明访问权限仍然有效 |
| 内容及原名映射缓存 | 按 origin、规范化 raw path、加密规则和对象代次复用，不因本地 token 变化重建 |
| 上游认证 | 保留正常工作所需的认证；不为了提速让所有请求改用管理员账号或把凭据发送到无关 CDN |
| 新鲜度 | 接受有期限的稳定对象假设；本程序写操作立即失效，外部修改可手动刷新 |
| 原名冲突、未完成上传、错规则 | 仍不能随便选一个文件或把半成品当可播放成品 |
| V3 tag 校验、Range/长度、取消、内存上限 | 保留；这些是正确性和流畅度，不是可以删除的负担 |
| 上传同名防覆盖及历史记录 | 不放宽，不删除，不因本地模式自动开放 rename/move/copy/resume |

不承诺无版本号/可靠验证器时立即识别“外部工具同路径、同大小替换”；接受该性能取舍，并提供单文件/目录刷新。也不降低现有 KDF 参数、不跳过 V3 认证、不重新加密已有文件。

## 4. 实施顺序

`LP0 基线与协议 → LP1 原名索引和快读 → LP2 元数据/直链复用 → LP3 解密热点 → LP4 前台优先 → LP5 真机验收与部署`

LP1、LP2 是主要收益来源，优先交付。LP3、LP4 只实施基线测量证明有价值的调整，不为“优化”无限堆缓存和预热。

### LP0：先量清楚，修正播放器协议体验

**工作：**

1. 固定同一手机、播放器版本/设置、网络、源、文件和测试顺序，分别记录 Docker 与 Android 内置服务结果。
2. 区分应用缓存冷/热、进程重启后首次访问、直链过期、元数据热但数据块冷；不能用“清本地缓存”冒充清除了网盘/CDN 缓存。
3. 采集各段耗时和次数：原名查找、额外 DAV、fs/get、HEAD、元数据 Range、实际媒体 Range、KDF 执行、等待队列、首个解密正文写入。
4. 所有入口核对同一明文长度：Depth:0、Depth:1、HEAD、GET 200、GET 206/Content-Range；覆盖 V1/V2/V3、空 V3、suffix/open-ended Range 与 416。
5. 复测上述 32 字节差异；若确认修复，禁止把 `Content-Length` 单独改小却仍输出原 XML/body 长度。
6. 目录带/不带末尾斜杠按实际资源类型处理，不靠文件扩展名或全局补 `/` 猜测；跳转不丢 Depth、认证及 PROPFIND 方法。

**交付/门槛：** 可重复脚本、请求计数报告、协议回归；本机现状表与 Android 对照，明确首帧是否有真机证据。新增采集不引入逐字节日志或前台同步落盘。

### LP1：原名反查索引 + 本地快读模式

**工作：**

1. 新增独立、版本化、可重建的反向读索引：`(origin, originalPath) → candidate record IDs`。记录 ID 再关联 primary record，不复制成新的唯一真相。现有写反查索引包含 auth/rule 的哈希，不能直接当作无读取凭据的查询索引。
2. 回填索引与更新采用一致事务/版本发布；`ReserveFilename`、完成/失败状态变更及已有记录维护路径同步更新。保留同原名多个候选，不能用最后一条覆盖冲突。
3. 首次回填允许线性扫描一次，但不能让每个 GET/HEAD/PROPFIND 都扫描。索引必须有未就绪/构建中/就绪/需重建状态；未就绪的 miss 不代表无历史记录，也不能静默退回逐请求 fullscan。构建期间优先用仍有效的完整旧索引；raw 映射加 primary 点查仅在已有完整代次确认其唯一性时可用，不能用单条缓存绕过尚未完成的冲突检测。确实无可用映射时给出明确短暂重试状态，而不是错误404。回填要显示进度，不对所有播放请求持长写锁或排队等待全库扫描。
4. 完成查询后做小容量内存热点缓存；正/负结果在上传和状态变更后同步失效。索引损坏只重建索引，原名审计、占位和完整原名不能清空。
5. `trusted_local` 下索引确认 complete/current rule 后直接绑定 raw path，取消原名读取前的额外 Depth:0 验证。注意不要误删上传完成核验使用的同名 helper。
6. PROPFIND 只发真正需要的一次上游查询；HEAD/GET 进入正常直链/解密链。不能为了去掉 preflight，又在别的 helper 加一次等价验证。
7. 明确区分“路径候选已解析”与“已远程鉴权”，修改内部状态命名，不能沿用假的 verified 标志让下游错误理解。
8. 保留 `standard` 模式与旧记录兼容；旧二进制回滚后再次升级时索引必须重建/校验，不能信任可能未被旧代码维护的派生数据。

**验收：**

- 1千/1万/10万记录，命中、未命中、重复原名、首尾候选都不在热请求中全表扫描。
- `trusted_local` 下原名解析额外上游请求数为 **0**；单文件 PROPFIND 非缓存命中仅有一次必要的上游 PROPFIND。
- 同一对象换 Basic/token 后不再因上传身份不同而 404，也不清空内容缓存。
- 并发上传完成与读取、失败记录、冷启动、索引中断重建、规则切换和 literal `%2f` 等路径不误映射。
- 本机稳态索引命中 p95 目标 ≤5ms；目标需固定设备实测，不能用共享 runner 绝对耗时作门禁。

### LP2：统一内容身份，复用元数据和直链

**工作：**

1. 复用现有根端 `ContentMeta` / FileMetaStore，不从目录大小猜测完整加密格式；目录快照、原名索引、内容几何、直链各自独立。当前 `FileInfo` 同时承载 geometry/RawURL，transport size 写入依赖 DAO 合并语义；实施时明确明文长度、密文长度和传输响应长度的来源，不能让一次 URL 解析覆盖正确的明文大小。
2. 内容缓存身份：配置 origin + 规范化 raw path + 规则指纹 + 对象代次/已知版本。可信本地模式不纳入本地 token，带签名 CDN URL 不作为内容身份。
3. 元数据与大小共享一次冷检查；同对象的并发 HEAD/GET/Range 合并必要的探测，不能每个请求分别跑完整 HEAD→PROPFIND→Range 链。
4. 调用者取消只退出自己的等待；全部取消后可取消尚未需要的网络任务，不让遗留任务占满连接。V3 等实际 CPU 工作仍按真实完成释放槽位。
5. 已确认完整元数据可持久化，重启可复用；老记录缺 nonce/chunk/KDF 参数时重新检查，不按当前默认值补齐。
6. 起始建议：确认几何复用期 24h，可配置；显式刷新及本程序写操作不受 TTL 限制。此数值是稳定对象假设，不是内容未变证明。
7. 直链按实际到期时间更新，未知有效期先沿用有限 TTL（建议上限 30min），同对象合并换签请求。过期前小幅裕量即可，不每次播放都主动刷新。
8. URL 换签只更新传输缓存；规则、内容尺寸、可比 validator/版本冲突或本程序修改才失效相关内容缓存。
9. 401/403 等证据与签名过期分别分类：签名直链过期可合并刷新一次，OpenList 账号拒绝不循环登录/重试。
10. 只在下游成功响应尚未提交时进行受限恢复；流中断不拼接新响应或从错误偏移继续。客户端重发正确 Range 时再恢复。

**验收：**

- 热元数据 + 有效直链：除实际媒体 GET 外，metadata-only HEAD/PROPFIND/Range/fs/get 为 **0**。
- 热元数据 + 直链失效：一次合并换签，不重复探测未变化的几何，不出现重试风暴。
- 16 个同对象冷请求：每代只发生一组必要元数据检查；V3 头/尾可能是两个必要请求，不能硬称冷启动全格式只有一次。
- 通过代理上传/删除后、切换规则后及手动刷新后，不返回旧几何；以 generation/epoch 阻止失效前的旧 flight 重新发布，失败响应不得污染成功缓存。
- 重启后热几何仍可复用；过期的持久直链不能当作有效直链。

### LP3：减少解密热点的 CPU、复制与网络读放大

**先测再改：**

1. 核实已有 KDF 路径是并发合并、完成结果缓存还是仅活动任务合并，按执行次数而非函数调用次数判断重复派生。
2. 仅在存在重复派生时加有界进程内 key cache：以口令指纹、nonce、算法和迭代参数区分；不把 key 写磁盘，也不改文件中的 KDF 参数。
3. 复用现有 V1/V2 明文块与 V3 已认证 record 缓存；可信本地命中可直接返回，不为本地缓存再发 DAV。V3 未命中仍读完整必要 record 并校验 tag。
4. 比较 V1/V2 块大小 64/256/1024KiB 与缓存容量档位；V3 保持原文件 record/chunk 几何，不假装配置小块就能减少实际认证 record 读取。
5. 测内存分配、全局锁等待、逐块复制和 GC；有证据才改缓冲复用，保持各请求数据独立。
6. 容量按进程总账核算：明文缓存、V3 pinned/resident record、在途密文、KDF 队列和预取共同计量。已有 64MiB record cache 等必须计入，不能多个“256MiB”叠加后只报一个数。

**验收：** 热重复区间不重新下载、不重复派生；密文截断/tag 错误绝不输出假明文；改变规则/对象代次后不命中旧块；1/4/16 路读取及取消无持续增长或串流串数据。

不默认把所有缓存调到最大。新增缓存驻留预算先以 ≤256MiB 为试验上限，再结合本机 RSS/容器限制收敛；该数值不是整个进程内存上限或必定需要的配置。

### LP4：前台优先，后台少做无用功

**工作：**

1. 统一登记前台播放、元数据探测、目录同步和邻集预热，复用现有调度，不再平行新建一个无界队列。
2. 限制后台在途任务，为前台保留连接/并发容量；前台有需求立即停止投放新的后台任务。已经进行的任务按可取消点退出，不能宣称可以瞬间抢占 CPU/网盘请求。
3. 不再因显示目录就给每个文件做 HEAD/Range/KDF。目录原名来自已有索引，几何缺失按需探测，不让小概率旧文件拖慢全部目录。
4. 首轮不启用视频正文预取。只有有可信“下一项”且测出收益时，允许一个有字节/时间预算的邻项任务；猜不到下一项就不做。
5. 冷目录必要时刷新；热目录可短时返回快照并在后台合并一次刷新。提供用户“刷新当前目录/文件”，新上传立即失效对应快照，不设无限期旧目录。
6. 负缓存采用短时退避，上传/刷新立即清除；不能让一次临时404造成“文件后来存在却两小时不能播”。具体 TTL 由失败类型与实测确定，不机械全设 0。

**验收：** 与后台全部关闭相比，后台开启的前台 TTFB p95 目标回退 ≤10%；目录 1800/1万项不发生逐项媒体探测；连续切集/退出/拖动后队列、连接及 goroutine 回归稳态。

### LP5：真实体验验收、发布和本机切换

1. 使用独立 `agent/*` 分支、Draft PR；快速格式/定向测试后跑完整 Actions，失败只修相关日志，不能因本地使用跳过正确性/race 检查。
2. 分批合并，确认每个最终 main workflow，不能把 PR 容器 build 成功当成镜像已发布。
3. 选定可验证修订的固定镜像 digest，保留旧镜像与配置；compose 仅更新本服务，不顺带更新 OpenList/MySQL或其他容器。可回退配置模式，不依赖可变 latest 标签猜版本。
4. 先下载并核对镜像，再短暂停服务做挂载文件的一致备份。区分 Bolt/JSON 备份和 MySQL 备份；没有 DDL 的性能改动不顺便升级数据库。
5. 明确处理自动更新器，避免 Watchtower 在验收期间把镜像再次换掉。回滚不仅复原标签，也需确保 compose 本服务以旧 image/digest 重建，禁止误触依赖服务。
6. 先启用索引，随后启用可信本地快读，再逐项启用其他优化；每一步记录变化，出问题可定位。
7. 保存运行 image ID、RepoDigest、revision、配置差异及回退 digest；若更换 APK，同时记录 APK hash。手机实测通过后发布报告；未有手机测量的版本只标注“服务端验收”，不得称“已实现手机秒开”。

## 5. 验收工作负载与指标

### 5.1 固定测试矩阵

| 场景 | 最低要求 |
|---|---|
| 当前问题文件 | WA-596.part003：信息查询、首段/中段/尾段、暂停续播和拖动；part004 不存在不得伪造成功 |
| 加密兼容 | V1/V2/V3，含空 V3、非默认 chunk/KDF 参数、长名/短名、literal 百分号路径 |
| 缓存状态 | 应用冷、热、重启后几何热、直链过期、数据块淘汰 |
| 操作 | 首次打开、立即重开、10%/50%/90%及尾部跳转、快速连续拖动、下一集、退出重开 |
| 并发与后台 | 1 路体验优先；4/16 路范围请求压力；后台关闭/开启对照 |
| 目录与审计规模 | 现场约1800项目录、1万项合成目录；1千/1万/10万原名记录 |
| 异常 | 上游慢/断流/忽略Range/直链失效、临时404、错密钥、截断、配置切换、进程重启 |

同一测试会话中，请求路径与上游响应种类固定；性能脚本不创建/重命名/覆盖真实用户云盘文件。写入/冲突测试使用明确隔离的测试目录与合成数据。

### 5.2 如何判定通过

- 协议/明文：自动夹具比对完整字节和分段字节，长度/Range不混用密文值；实际内容不可用时不补成功响应。
- 请求数：按 LP1/LP2 的“额外请求为0/并发合并”契约自动断言，比不稳定的云 runner 秒数更重要。
- 服务端延迟：固定本机至少记录30个冷/热样本的 p50/p95；上游 RTT、返回码、下载字节量同时记录，不只报最好一次。
- 手机体验：同设备/播放器/网络/源，Docker基线、优化版、Android内置服务交错测试；至少10次冷/热打开与10次拖动，报告中位数/最大值及原始样本，不把小样本分位数当稳定容量承诺。
- 改善目标：以基线为准，优先消除额外串行往返；不承诺所有网盘、所有V3文件固定1秒首帧。热路径不得有可复现明显回退；首帧和拖动结果接近安卓对照的程度单独报告。
- 长时间：代表性大文件连续播放 ≥60min、100次混合打开/拖动压力、取消及重启；无错误字节、增长性泄漏和非预期中断。手机物理卡顿需单独记录，不能只看服务端206数量。
- 资源：报告 RSS/heap、GC、CPU、网络放大、连接与队列；后台默认和缓存大小只有在收益与资源成本都可接受时才进入部署配置。

## 7. 与旧工程计划的关系

- `REMAINING_ENGINEERING_PLAN.md` 保留历史目标，不因为本计划就宣称 P0–P9 全部完成。
- 本轮优先级变为上述 A→B→C→按测量选D/E→F。多用户权限重新证明、分布式写协调/HA、严格实时新鲜度、全驱动改造等不作为本轮播放优化前置条件。
- 旧计划中未合并的 P5 等分支若与本地缓存策略冲突，实施前重审；不能把“每请求严格验证”又合进 trusted_local 热路径。
- 备份可恢复性、原名完整性、避免覆盖、对象代次、取消及正确解密继续保留，因为它们影响数据和播放稳定性，而不是以安全为名增加往返。
- 本轮不自动暂停/关闭旧 PR、不自动部署；计划批准后才按批次执行并更新进度证据。

## 8. 完成定义

只有同时满足以下条件，才称“本地播放优化完成”：

1. 原名读取热路径不全表扫描，可信本地模式不增加播放前 DAV 验证。
2. 热元数据/有效直链不重复探测，并发同对象冷请求合并，失效后能受限恢复。
3. 原有文件正确打开，长度/Range一致，写保护与原名历史不受损。
4. 背景工作不明显拖慢首帧或拖动，内存和并发有实测上限。
5. 完整云门禁、main发布及固定镜像本机验收完成，回滚可操作。
6. 手机测试完成则给出真实体验结论；没有真机结果则明确保留 `device_unverified`，不使用“最佳”“全场景秒开”等无法验证的结论。
