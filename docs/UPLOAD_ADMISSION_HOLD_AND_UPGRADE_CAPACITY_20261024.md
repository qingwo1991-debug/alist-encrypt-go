# 上传准入紧急暂停与后续升级容量门槛（2026-10-24）

## 新发现：不能把上传后读回当作上传前整片解码

只读审计实际 systemd 启动入口及运行配置的白名单字段，确认生产上传器的 `upload.full_media_decode_before_upload` 为布尔 **false**，`slice_enabled=false`。新上传验证把该配置传入媒体校验器，因而跳过整片 FFmpeg 解码分支。现有结构 / 包采样检查、来源稳定性、云端完整 SHA256 读回和持久化收据 / 删源门禁仍有价值，但它们**不能替代上传前确认整片可解码**；此前若将实际生产描述成强制整片解码，应以本次核实更正。

2026-10-24 **03:41:47 UTC**，父代理先确认上传健康为 idle、active_upload=0、active_verify=0，再仅停止 `alist-uploader.service`；当时 systemd 为 inactive / dead。**这次 stop 并非持续封锁**：约 03:47 复核时服务再次 active，夜间控制器仍能启动它。不能声称这段间隔绝无上传；两次 idle 快照不是完整区间审计。

父代理于 **03:48:03 UTC** 停止夜间 timer / oneshot 控制器，再停上传器，健康快照仍为 idle / upload=0 / verify=0。尝试的 runtime mask 虽创建了 `/dev/null` 链接，实际 LoadState 仍为 loaded，**未把它算作有效屏蔽**。随后新增持久化 systemd drop-in `90-admission-safety-hold.conf`，要求一个目前不存在的 `/run/alist-uploader-admission-reviewed-20261024` 审核标记；03:49:00 reload 后实际请求启动，服务被条件拒绝，`ConditionResult=no` / inactive，确认不再只依赖单次 stop。未创建审核标记；夜间 timer 和控制器也保持 inactive。重启后 `/run` 标记仍缺失，条件继续失败关闭。该门禁是显式服务配置变更，不是网关或上传凭据配置变更。

没有删除源、修改云对象或停止网关。暂停是风险控制，不是修复完成。恢复条件包括强制整片验证、来源流 TOCTOU 补强、离线回归及独立审查通过，再明确移除门禁并评估恢复；不能在维护收尾时盲目恢复旧状态。

该暂停发生在 600 秒实时解码观测期间，是明确的并行负载变化，必须在对应报告中披露。不能继续声称那次观测全程保持上传器运行，或将内存变化当作严格对照。

最小代码修复已将新视频入口固定调用 `validate_media(..., full_decode=True)`，不再接受旧 false 配置绕过；源码摘要 `79725ff718534fc2f9780c47e75e2411d6b45e01bfa4440b791d1e195b6d8b46`，语法检查与五项无网络回归通过。原脚本以私有 0600 副本保留。该最小修复**还不足以解除门禁**：内存夹具重现了验证通过后、容量检查与 PUT 打开路径之间替换字节会先到达云写入；后续 SHA / 指纹能阻止交付承诺和删源，却不能撤回已发送字节。来源流补强仍在独立私有副本实施，没有部署或宣称解决。

Torrent 完成状态 / 选择文件计数与位图门禁也不等于独立 piece 重哈希。本记录不冒称已修复 TOCTOU、torrent 分片证明或所有未来损坏媒体，也不以暂停服务代替最终交付。
